## 观察与原因假设

RC4 的候选 CI 用时11分45秒、完整L3用时14分44秒，原依赖图强制串行；两者均只读冻结源码，
无共享写资源。并行后预期关键路径取较慢阶段，但不宣称未经实测的节省时间或成本下降。
并行会在一个阶段失败时仍消耗另一阶段资源，接受该有界成本；每个job仍有既有硬超时。

发布前 stable/previous-preview 快照已真实写入 runner临时目录，却只在下游公开验收artifact留存。
RC4公开验收被跳过时原快照未上传，只能明确标注重构输入后恢复。跳过条件已在main修复；
本提案补齐独立早期原件留存，防止任何后续发布/验收失败再次丢失原发布前输入。

## 最小方案与备选

候选CI与完整L3同时依赖冻结输入，promote显式等待两者成功；后续main CI、Release、镜像、
公开浏览器验收的顺序、权限和成功断言不变。早期snapshot artifact上传失败直接阻止后续发布；
稳定版不生成预览快照。末尾always归档仍保存失败原件。

直接省略候选CI被拒绝：当前push CI查询未绑定差异基线、attempt/job和完整环境，不能证明等价。
缓存调整留作后续：仅有固定Go/go.sum cache命中和race耗时，尚不能证明重复冷编译的因果。
不增加第二套发布入口、自有服务器、WSL、生产部署、CF准入或业务权限变化。
