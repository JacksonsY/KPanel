## 观察证据与原因

`release-public-verify.yml` 与 `verify-github-public-release.mjs` 只接受 RC，而稳定 Release 的公开验收 job 被跳过。
这与现有稳定/预览同样验收的契约不一致，是可重复的入口缺口，非单次网络失败。
RC23 另有旧 MCP 测试要求100ms内直接返回终态，与接口允许返回 executing 的契约不符；只调整测试等待，仍验证最终 unknown 和不重复写。
浏览器偶发动态模块加载失败的根因未唯一定位；本轮增加失败取证，不重试加载、不清空错误或放宽窗口恢复断言。

## 范围与非目标

- 扩展原公开验证入口接受规范稳定版本；稳定版验证 latest/GitHub Latest 已提升且 preview 保持原RC，预览版仍验证 stable 不变。
- 两种通道均保存原始发布前快照，核对候选、版本、双架构、15附件、11校验项和公开浏览器。
- 稳定升级从上一RC的真实后端按默认 stable 通道发现正式版，保留 opt-in/退出、失败安装及未自动安装断言。
- 不修改产品权限、默认安装、依赖或Docker配方；不重建或覆盖不可变版本镜像。
- 增加仅限 `main` 的人工恢复入口，必须绑定原始发布 `run-id/attempt`、候选SHA、稳定版本及不可变镜像摘要。它核验 `release.yml` 的精确稳定标签 `push`、标签名及与候选相同的控制器SHA；预览版dispatch不接受稳定版本，不属于本恢复入口。只接受“镜像提升成功、GitHub Release 发布步骤失败”这一故障组合。
- 在通道提升前冻结全部15个Release附件的名称、大小和SHA-256，并将清单摘要写入原始发布身份工件；恢复时逐项比对公开草稿，确保完整附件集与原运行一致。
- `publish-draft` 只发布原始运行已创建的同一草稿，且仅在 `latest` 仍指向目标摘要、GitHub Latest 仍是快照版本、`preview` 未改变时执行；已完整发布时只重跑只读公开验收。
- `restore-latest` 只可在 Release 仍为草稿且 GitHub Latest 未改变时，将 Docker `latest` 恢复到冻结快照的既有摘要；不改动版本镜像、Release草稿或其他标签。任何身份或公开状态不确定均失败关闭。
- 恢复发布权限按操作拆分：草稿发布只授予 `contents:write`；镜像回退仅使用 Docker Hub 凭据并保持 GitHub `contents:read`。写入前再次核验全部身份与公开状态。

## 规范验收合同 v1.0

- 精确规范基线：上述RC23中的 PROJECT_RULES.md 5.1/5.2/5.3、docs/release-channels.md、现有唯一公开验收入口。
- 冻结的允许范围：原公开验收脚本/调用工作流、相应定向回归、异步MCP测试、治理复核日期；不改规则阈值。
- 权威入口和正常授权路径：候选同SHA CI与非作者复核后集成main；稳定tag触发GitHub-hosted L3和Release。
- 正确性：稳定版必须 non-prerelease/Latest，version/latest摘要一致；预览版仍prerelease且stable保持不变。
- 一致性：API、镜像、标签、正文和浏览器均绑定同一候选与digest，不将当前通道重建为旧快照。
- 完整性：保留15附件/11校验、双架构、原始失败与全部浏览器断言。
- 可执行性：Node定向回归、Linux同SHA CI、正式版新L3、公开真实浏览器均成功。
- 效率与比例性：复用同一入口与既有RC证据，不重审已recorded的安全包，不新增常驻任务或扫描器。
- 可演进性：预览与稳定分支断言独立，原失败不可覆盖；不合格候选可回退到RC23和配套镜像。
- 停止条件：新增紧急/高确认漏洞、通道身份不一致、冻结源树漂移或公开产物不确定时停止发布。
- 范围外发现：记录独立待办及期限，不混入无关产品变更。
