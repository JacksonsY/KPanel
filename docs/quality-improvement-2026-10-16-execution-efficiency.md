## 观察证据

- 10 月记录中存在可在长验证前发现的输入与环境异常。`v1.27.0-rc.1` 验收明确保留本机治理套件 308 项中 304 通过、4 失败：三个缺少 Go，一个 vendor CRLF 原始字节不匹配。该记录以精确文档 SHA 的 Linux CI 补验，没有删测试。
- 本轮在管理工作树、原始 PATH 下复现同类故障；原始日志保存在仓库外 `C:/GitHub/_task-evidence/kpanel-october-execution-efficiency/`。新候选使用同一管理工作树输入及相同 PATH 运行固定预检，提前汇总 native Go、Bash Go 与 vendor 字节失败；没有执行后续测试，也不把预检退出码当作业务通过。
- Windows、Node 24.17.0、Git for Windows Bash。修复环境使用已有 Go 1.27.2 的进程 PATH。独立 checkout 仍有 30 个 vendor 文件为 CRLF，普通重检出未恢复原字节；仅在本任务 worktree 从 HEAD blob 逐项恢复并回读摘要，刷新索引后 vendor 无差异。r1/r2 失败和 `checkout-bytes-receipt.json` 保留，r3 固定预检全部通过（479ms）。没有修改管理工作树、vendor 清单或共享 Git 配置。
- 这些不是只出现一次的假设：发布验收与本轮复现相互印证。路径猜测、跨 Shell 参数错误等历史记录说明应复用已验证入口；它们不证明所有耗时均由同一原因造成。
- 数据缺口：尚无可比的逐任务准备、有效验证、外部等待和返工时长序列。RC 数量增长不能单独证明质量下降或冗余；不能用门禁失败发现提速推算整体开发提速。

## 原因假设

- 治理套件运行到后段才暴露可廉价发现的必要条件，造成无效长跑；角色交接时重复执行有效门禁、同输入重试及过早冻结 RC 可能额外放大成本。
- 替代解释：功能范围、风险、上游等待和故障复杂度增加；新增真实缺陷需要新的 RC。不能为减少次数合并无关范围或延迟紧急修复。
- 可证伪：固定预检没有提前暴露已知故障、误拒支持环境，或后续可比样本返工未下降，即不支持对应收益；必要验证的耗时不得作为“浪费”扣除。
- 不触及 `kejilion.sh` 业务真源、真实系统资源、Panel/Agent 权限边界、依赖 pin 或兼容契约。

## 最小改动方案

- 复用 `task-preflight.mjs governance`，固定命令分别探测 Node、Git、native/Bash Go，单个进程最多 5 秒；Go 探测禁止自动工具链下载。检查唯一门禁列出的测试文件、必要输入及原有 vendor 字节校验，汇总全部可检测失败。
- `verify-governance.sh` 在所有耗时步骤前自动调用，不提供跳过开关。测试清单来自该脚本；源校验复用原实现，不归一化摘要或维护第二清单。
- 规范明确成组定位输入、先修确定性原因再重试、同 SHA/环境/工具/参数的有效证据可复用，以及授权范围内当前负责人闭环。独立判断、变化后的补验和不同证据层级不被取消。
- 未公开同范围微调先形成本地候选，适时发 RC；紧急修复、明确要求及时预览和独立定位不受固定等待限制。每个实际 RC/稳定版继续完整 L3。
- 复用现有交付及提案更新状态与实测，不为小任务新增统计文档；保存原始失败，缺失值不作成功或零成本。
